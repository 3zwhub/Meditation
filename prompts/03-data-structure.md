# 3단계 프롬프트: 데이터 구조와 시스템 설계

> 사용법: 1단계 결과물(설계도)과 2단계 결과물(모듈 스크립트 중 2~3개 샘플이면 충분)을 아래 칸에 붙여넣고,
> `[구현 환경]`을 채운 뒤 구분선 아래 전체를 AI에게 붙여넣으세요.
> 이 단계의 목표는 4단계 구현에서 **그대로 코드로 옮길 수 있는 설계 명세**를 만드는 것입니다.

---

## 역할
1단계와 같은 팀으로 생각하되, 이번에는 **소프트웨어 아키텍트이자 데이터 모델러** 역할이 가장 중요하다.
임상심리학자는 설계가 치료 원칙과 안전 기준을 지키는지 검토하는 역할을 맡는다.

## 배경
1단계에서 우울·불안을 지속적으로 개선하기 위한 통합 프레임워크를, 2단계에서 모듈별 스크립트를 만들었다.
이번 단계에서는 이 콘텐츠와 사용자 기록을 담을 **데이터 구조**와, 상태 판별·추천·측정이 돌아가는 **시스템 로직**을 설계한다.

## 1단계 결과물
[1단계 결과물: 메커니즘 지도, 상태별 라우팅, 루틴, 측정, 안전 장치, MVP 범위]

## 2단계 결과물 (샘플)
[2단계 모듈 스크립트 2~3개. 형식(A~E)이 드러나면 충분]

## 구현 환경
- 산출물 형태: [예: 모바일 앱, 웹앱(PWA), 노션/스프레드시트, 아직 모름]
- 사용자: [예: 나 혼자 / 소수의 지인 / 공개 서비스]
- 기술 선호: [예: React + TypeScript, Flutter, 코딩 경험 적음 → 노코드, 상관없음]
- 데이터 저장: [예: 기기 안에만(오프라인), 클라우드 동기화 필요, 상관없음]

## 이번 단계에서 할 일
구현 환경이 비어 있거나 설계에 큰 영향을 주는 정보가 빠져 있으면, 질문을 최대 5개까지 먼저 해라.
답을 받은 뒤 아래 항목을 순서대로 작성한다.

### 1. 콘텐츠 데이터 모델
2단계 모듈 형식(A~E)을 그대로 담을 수 있는 구조를 설계한다.
- 엔티티: 모듈, 모듈 단계(스텝), 질문/입력 필드, 확언, 루틴, 조합 시퀀스, 기법 출처, 메커니즘
- 각 엔티티의 필드, 타입, 필수 여부, 관계(1:N, N:M)를 표로 정리한다.
- **완성된 예시 1개**: 2단계 샘플 모듈 하나를 실제 데이터(JSON 또는 선택한 형식)로 변환해 보여준다.
- 콘텐츠를 코드와 분리해서, 나중에 스크립트를 고치거나 모듈을 추가할 때 코드를 건드리지 않아도 되게 한다.

### 2. 사용자 기록 데이터 모델
- 일일 체크인(기분·불안·에너지 0~10, 메모), 모듈 수행 기록(시작/종료 시각, 전후 점수, 작성 내용), 저널 항목,
  척도 검사 결과(PHQ-9, GAD-7), 루틴 설정, 위기 신호 기록
- 각 엔티티의 필드, 타입, 관계를 표로 정리하고 예시 데이터 1개씩을 붙인다.
- 나중에 분석하기 쉽도록 시간대, 상태, 사용한 모듈을 일관되게 기록하는 규칙을 정한다.

### 3. 상태 판별과 추천 로직
1단계 상태별 라우팅을 **실행 가능한 규칙**으로 바꾼다.
- 입력: 체크인 점수, 사용자가 고른 상태, 시간대, 가용 시간, 최근 수행 기록
- 출력: 추천 모듈 1개 + 대안 2개, 각 추천 이유(사용자에게 보여줄 문장)
- 규칙은 의사코드 또는 결정표로 쓴다. 머신러닝 없이 **설명 가능한 규칙 기반**으로 시작한다.
- 같은 모듈만 반복 추천되지 않게 하는 규칙, 사용자가 추천을 거절했을 때의 처리
- 2주 이상 데이터가 쌓였을 때 "나에게 효과가 컸던 모듈"(전후 점수 변화 기준)을 반영하는 개인화 규칙

### 4. 측정과 피드백 로직
- PHQ-9·GAD-7 실시 주기와 점수 구간별 해석 문구(진단이 아니라 참고용임을 명시)
- 주간 리뷰 화면에 보여줄 지표와 계산 방법(예: 주간 평균 기분, 모듈별 평균 전후 변화, 루틴 수행률)
- 1단계의 조정 규칙(예: 2주간 효과가 없으면 무엇을 바꿀지)을 로직으로 정리

### 5. 안전 로직 (가장 엄격하게)
- 위기 신호 감지 조건: PHQ-9 9번 문항(자해·자살 생각) 응답, 체크인 점수 급락, 저널에서 사용자가 직접 표시한 위기 상태 등
- 감지 시 동작: 어떤 화면을 즉시 띄우고, 어떤 기능을 잠시 멈추고, 어떤 안내(109, 1577-0199, 119)를 보여줄지
- 자동 텍스트 분석으로 위기를 판단할 경우의 한계와 오탐·미탐 위험을 적고, MVP에서 할지 말지 권고한다.
- 안전 로직은 다른 규칙보다 항상 우선한다는 원칙과 그 구현 방법

### 6. 개인정보와 데이터 보호
- 정신건강 기록은 매우 민감한 정보다. 저장 위치, 암호화, 잠금(PIN/생체인증), 백업·내보내기·완전 삭제 기능을 설계한다.
- 공개 서비스라면 한국 개인정보보호법상 민감정보 처리 시 유의점을 요약한다(법률 자문이 아님을 명시).
- 외부 서버나 AI API로 데이터를 보낼 경우 무엇을 보내고 무엇을 절대 보내지 않을지 정한다.

### 7. 화면 흐름과 아키텍처
- 주요 화면 목록과 이동 흐름(홈 → 체크인 → 추천 → 모듈 진행 → 마무리 기록 → 홈), 텍스트 와이어프레임으로
- 컨디션이 최악일 때를 기준으로, 앱을 열고 **2번 탭 안에** 최소 버전 모듈을 시작할 수 있게 설계한다.
- 구현 환경에 맞는 기술 스택 추천과 폴더 구조, 주요 컴포넌트/모듈 분리 방식
- 오프라인 동작, 알림(루틴 리마인더) 설계와 알림이 압박이 되지 않게 하는 원칙

### 8. 4단계 구현 계획
- MVP를 구현 가능한 작업 단위로 나누고 순서를 정한다(각 작업의 완료 기준 포함).
- 테스트해야 할 핵심 시나리오(특히 추천 로직과 안전 로직)
- 4단계에서 사용할 프롬프트 주제 목록

## 작성 원칙
- 한국어로 쓰되, 필드명·코드·의사코드는 영어로 쓴다.
- 1·2단계 결과물과 **용어와 ID를 일치**시킨다(모듈 ID, 상태 이름, 메커니즘 이름).
- 과도한 설계를 피한다. MVP에 필요 없는 것은 "나중에" 목록으로 따로 뺀다.
- 추천 로직이 치료적 판단을 대신하는 것처럼 보이지 않게 한다. 추천 문구는 "~해 볼 수 있어요" 같은 제안형으로 쓴다.
- 1·2단계 설계에서 구현이 어렵거나 모순되는 부분을 발견하면, 마지막에 **"이전 단계 수정 제안"**으로 따로 정리한다.
